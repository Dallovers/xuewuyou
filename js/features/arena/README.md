# 好友竞技场 · 擂台（板块 A 第二批）

2026-10-23 公共校园本地接入：已同步 PR #89 的知识竞赛台，保留 `sharedSite:true` 跳过独立草地/远景/浮尘、`return-bridge.js` 门外返回，以及两座甲乙牌均朝西的修正。公共宿主在 ready 后统一室外白石铺地，独立页维持本模块原材质；纸条的只读面板、拾取禁用与 Esc 在宿主接入。固定来源及实拍见 `docs/team/visuals/campus-round-v4/`，未推送或部署。

社交广场 README 里写着「好友挑战（`arena`）未改动，独立竞技场美术放第二批」，这就是那批：
**能从主站进入、能单独预览、能和社交广场并排预览、能按同一套 `createDistrict` 契约挂载的擂台空间 + 三个实物交互点。**

第二版补了入口与外壳：主站「校园互动 → 好友竞技场 → 进入 3D 好友竞技场」进独立页，
页面外壳（顶部工具条 / 左侧引导条 / 底部状态条 / 纸色对话框）照知识图书馆那一套，3D 画面本身没动。

第三版把面板接到真实业务、并做了触屏：擂台台阶按 E 读的是真实的挑战列表（能就地发起 / 开始 / 取消），
报名处读的是真实的搭子簿与待处理邀请（能直接接受 / 婉拒）；手机上是双指捏合缩放、单指转向、
54px 方向键，底部三层控件互不遮挡。3D 画面仍然一行没动。

不含：登台对打动画、观众 NPC、答题与复盘（要排数学式子，仍回主站）、夜间照明。

## 入口页操作

- 外观检视：拖动旋转、滚轮缩放（缩放上下限**按机位算**，见下）；左侧三个机位（西侧牌坊 / 擂台正面 / 报名处）
- 进入漫游：WASD / 方向键移动、Shift 快跑、拖动转向、J/L 转向、E 交互、Esc 回到外观
- 漫游的第一人称（第八轮）：视野 `37.9° → 46°`（冲刺 55°）、步态起伏 16mm + 横摆 9mm + 滚转 0.4°、
  站定有 3.5mm 的呼吸、起停带一阶惯性；顶层页面里点一下画面可以锁定鼠标直接转头（iframe 里不申请）
- 触屏：双指捏合缩放（仅检视模式）、单指滑动转向、左下方向键长按行走且按下有反馈、
  底部的 E 提示变成整条通栏并改口为「点一下…」
- 顶部「挑战规则」是静态规则卡；按 E 打开的是业务面板（擂台读挑战、报名处读搭子簿、锣是本地动作）

缩放区间（`zoomRange()`）：`min = max(3.2, 预设 × 0.7)`、`max = min(30, max(预设 × 1.7, 12))`。
写死一个全局 4.5~26 的后果是：擂台正面一捏就把相机送进围护里，报名处却几乎不能靠近——三个机位要读的关系差着三倍，
只能各留各的区间。

## 跑预览

ESM 需要 http，不能直接双击 HTML：

```powershell
# 在仓库根目录
python -m http.server 8099
# 主站入口页（新的，图书馆式外壳）
http://127.0.0.1:8099/js/features/arena/index.html
# 自测页（深色 HUD，带 ?with=social / ?x / ?yaw 等参数）
http://127.0.0.1:8099/js/features/arena/preview.html
# 和社交广场并排看
http://127.0.0.1:8099/js/features/arena/preview.html?with=social
```

入口页操作：拖动旋转 / 滚轮缩放 →「进入漫游」→ WASD、Shift、拖动、J/L、E、Esc。

自测页操作：WASD / 方向键移动，Shift 加速，拖动看向，J / L 转向，E 交互，Esc 关闭面板。

自测页参数：

| 参数 | 作用 |
| --- | --- |
| `?with=social` | 把广场一起挂上，擂台按 `ARENA_LAYOUT.neighbor.offset` 摆到东侧，两块场地的碰撞体、交互点合并成一套 |
| `?hud=0` | 隐藏所有覆盖层（截图用），不改交互与入口 |
| `?x= &z= &h=` | 直接站到指定坐标（`h` 改视高，默认 1.6） |
| `?yaw= &pitch=` | 角度制朝向。`yaw=0` 朝北（-Z），`yaw=90` 朝西，`yaw=-90` 朝东 |
| `?mm=` / `?fov=` | 等效焦距（默认 35mm，按 `2·atan(12/mm)` 换算成垂直 FOV）/ 直接给 FOV |

两个默认机位：

| 模式 | 机位 | 画面 |
| --- | --- | --- |
| 单开 | `x=-15.5 z=9 yaw=-50`，视高 1.6 | 站西侧栏外的草地上：匾额 + 开赛锣 → 围栏缺口 → 台阶与围台 → 四角竖幡 |
| 并排 | `x=-2 z=10 h=9 yaw=-45 pitch=-14`，视高 9 | 抬高俯视：喷泉与坐凳 → 广场铺装 → 接缝 → 牌坊（含吊锣）→ 擂台 |

朝向不按「对准台心」算：从栏外对准台心是 -62°，牌坊匾额会顶到画面左边缘；并排模式对准台心则广场只剩左下角一片铺装。
用 `?x` / `?z` 手动定位时仍按台心反算（那时候是在「走到某处看擂台」，不是看总览）。

验收用机位（脚本里实际跑的这几个，可复现）：

| 机位 | 参数 | 看到什么 |
| --- | --- | --- |
| 单开默认 | 无参数 | 西南 3/4，牌坊 / 缺口 / 台阶 / 围台 / 竖幡同框 |
| 并排默认 | `?with=social` | 广场与擂台并排的总览，能数出接缝和围栏缺口 |
| 台阶前 | `?x=-5.2&z=0&yaw=-90&pitch=1&h=1.72` | 正对上台口，按 E 的提示和业务面板同框 |
| 报名处 | `?x=5.1&z=4.6&yaw=-90&pitch=-4` | 柜台主面、立牌、5mm 柜门缝 |
| 牌坊与锣 | `?x=-12.2&z=-1.5&yaw=-90&pitch=8` | 匾额、主梁、檐口、吊在梁下的锣（锣面正对进场方向） |

**不要用正对门洞的机位**：门和擂台在同一条轴线上，正着看两者必然互相遮挡，而且西立面背光，
整座牌坊会是一块黑剪影。要斜着看。

## 挂到主站

```js
import { createDistrict, ARENA_LAYOUT } from './js/features/arena/arena-district.js';

const arena = createDistrict({
  THREE,                 // 复用公共 three，不在这里 import 第二个
  materials,             // 可选：按材质 ID 传统一材质库
  openFeature,           // 可选：统一桥接；不给就回退到现有 WG_Community.open
  mode: 'mounted',
});
arena.root.position.set(...ARENA_LAYOUT.neighbor.offset); // 摆在广场东侧
scene.add(arena.root);

// 主循环里
arena.update(dt);
// 卸载时
arena.dispose();
```

要点：

- 模块**不自建 renderer、不启动 RAF、不动公共相机与输入**；`update(dt)` 由宿主调用，`dt` 内部夹到 0.1s。
- `colliders` 用的是 **root 局部坐标**。root 一旦被位移，宿主必须像 `preview.html` 那样把 `center` 加上 offset 再判碰撞。
- `dispose()` 幂等；释放自己创建的几何（含 UV 缓存与倒角几何）、材质、CanvasTexture，并把 root 从父节点摘除。宿主传进来的共享材质一律 `clone()` 成自有副本，原件不会被释放。
- `ready` 是 Promise，贴图异步补挂，不阻塞 `createDistrict` 的同步返回；需要截图/验收时 `await arena.ready`。
- 材质 ID 沿用风格文档：`stone_light / stone_light_in / brick_grey / metal_dark / metal_frame / roof_bluegrey / oak_light / oak_flat / fabric_greygreen / accent_amber`，
  额外自建 `arena_olive`（识别色，同 `js/campus-registry.js` 里 arena 的 `0x9a9e67`）、`bronze`（锣面）、`ground_paving / ground_lawn / leaf / soil`。
- 台基碰撞沿围护铺成四条、西门留空（第十三轮）：人可以从西侧台阶走上台面站着，
  但没有上台后的动作，挑战仍在 DOM 面板里作答。

| `arena.stage.yi` | 台面乙位站位线（半径 1.7） | 作答位 · 乙 → 按 E 就位作答 | 同上（乙位朝 +Z） | 同上 |

`it.action()` 仍然保留（`openFeature` → 回退 `WG_Community.open`），独立页只是**不走它**：
那一页没有主站的社区 DOM，调它只会拿到 `{ok:false, reason:'no-bridge'}`。独立页改为直接读接口，
宿主挂载（`preview.html`、将来的多板块宿主）照旧走 `action()`。

两个设计取舍：

- 擂台交互挂**台阶**不挂台心。台心到台阶口约 4.5m，半径得放到接近 5m 才够，那样看台第一排（距台心 4.5m）也会被误触发。挂台阶、半径 3.2，语义也更准——擂台只有西侧这一个上台口。
- 报名处开的是**搭子**不是挑战：挑战的前提是先有人可打。擂台负责「打」，报名处负责「先有人可打」。
- 两个作答位的锚点放在**站位**上，不放答题台本体。台子 0.88 高、占着台面，锚点落在台子中心时，
  人在台上走动会先命中台子，提示变成「这有个柜子」而不是「站到这里」。
  报的坐标是**板块局部**的（`root` 局部），宿主摆放时自己加 `root.position` —— hub 第一版漏了这一步，
  人当场被瞬移到庭院水池边（详见第十四轮）。

## 业务接口（独立页用，全部是既有接口）

| 动作 | 请求 | 用在哪 |
| --- | --- | --- |
| 读搭子与主题 | `GET /api/community/home` | 发起表单的下拉、报名处的搭子簿与邀请 |
| 读挑战列表 | `GET /api/community/challenges` | 擂台面板的「我的挑战」 |
| 发起挑战 | `POST /api/community/challenges` `{to, topic}` | 擂台面板 |
| 开始计时 | `POST /api/community/challenge/start` `{id}` | 擂台面板（列表里 `!mine.startedAt` 时） |
| 取消 / 婉拒 | `PUT /api/community/challenge/cancel` `{id}` | 擂台面板 |
| 处理邀请 | `PUT /api/community/request` `{id, action}` | 报名处（`accept` / `reject` / `cancel`） |

请求走主站的 `js/api.js`（`window.WG_API.req`），和主站共用 `xwy_token` 与同一套超时/重试/错误归一化。
代价是这一页多引了三个普通脚本（`deploy-config.js` / `runtime.js` / `api.js`），好处是**不新增任何后端接口**，
也不会出现第二份登录态。

三种会话状态分得很清，都不伪造数据：

- `guest`（没有 token）→ 面板说「还没有登录态」+ 一个去主站登录的按钮；
- `local`（`local.*` 的降级 token）→ 说「云端没连上，挑战发不出」；
- `cloud` → 顶部工具条出现昵称胶囊，面板正常读接口。

**答题与复盘仍在主站**：五道题要排数学式子（MathJax），3D 页里重写一遍渲染必然走形。
所以「在主站继续」是深链 `#community/arena`，落在主站好友竞技场那一栏，不是一句空话。

## 第五轮：往「照片级」推（2026-10-22）

这一轮的约束要先说清楚：**vendor 里没有后处理**。`vendor/three/` 只有 `three.module.js`、
`OrbitControls.js`、`RoomEnvironment.js`、`RGBELoader.js` —— 没有 `EffectComposer`、没有 SSAO / Bloom / DoF。
渲染管线是 `ACESFilmicToneMapping` + `PCFSoftShadowMap` + `sky.hdr` 经 PMREM 当 `scene.environment`，
就这些。所以「照片感」只能从别处来：**程序化微表面贴图、材质各向异性、空气透视、远景层次、镜头叠层**。

### 1. 修掉一个真 bug：围绳的旋转装反了

`ropeGeometry()` 的曲线沿 **X** 铺开（span 就是跨度）。但两道绳的循环写反了：
南北两道（`z = ±postR`）被转了 90°、东西两道（`x = ±postR`）没转。
结果是**每道绳都从场地中线往一边长出去**——半个擂台没有绳，另一半的绳穿到台外。

最明显的症状是站在正面对着擂台看时，画面正中有一条贯穿上下的白线：
那是绳管正对着镜头、透视收缩成一条。第四轮把绳从圆柱换成带法线的管子之后，
这个错误从「看起来有点乱」变成「一眼看见」，才被揪出来。

改法就是把两行的 `rotY` 换过来，一行注释写明原因。

### 2. 微表面：让材质在近处「有手感」

| 手段 | 用在哪 | 参数 |
| --- | --- | --- |
| `heightToNormal()` | 通用：给高度场中心差分求梯度生成法线，纹理可平铺 | — |
| `ropeNormal()` | ~~围绳~~：`sin(2π(6u+v))` 的斜纹 = 麻花 | **第十一轮随围绳一起删掉** |
| `weaveNormal()` | 台面帆布（护角垫包布已随垫子删掉）：`sin·sin` 48×48 经纬 | 帆布 `repeat 48,48 / 0.95` |
| `makeRoughnessNoise()` | 12 种材质（金属、石材、橄榄漆、布、铜、地面、帆布）挂同一张 4×4 循环噪声 | 底色接近白（`#f0f0f0`），只做 ±7 的抖动 |
| `makeRingCanvasMap()` | 台面：512 一张**不重复**铺满，边角积灰 + 86 道滑步擦痕 | 底色 `#bdb49d`（原来是 `#cdc5af`，在 0.8 曝光下烧成一片白纸） |

法线贴图必须 `colorSpace = THREE.NoColorSpace`；粗糙度图是和材质 `roughness` **相乘**的，
底色一旦压暗，整个材质就跟着变亮变哑。

### 3. 接地与脏：真实感最便宜的一半

- `grimeSkirt()`：台基四周四条向内渐隐的积灰贴片（`opacity 0.46`），墙脚不再是硬边。
- `makeGrassTexture()` + `grassClumpGeometry()` + `buildGrass()`：`InstancedMesh` 铺 182 处杂草
  （围栏外 92 + 56、场内 34），每丛 3 片交叉细叶。**西侧不放**——那边是并排的社交广场，接缝要干净。
- `buildDust()`：240 粒浮尘，`Points` + `additive` + `sizeAttenuation` + `toneMapped:false`，
  缓慢上浮并横向摆动。这一条对「照片」的贡献比想象中大：空气里有东西，画面才不空。

### 4. 远景：三层，替雾做空气透视

草地铺到 **200×180**（原来 36×32，18m 处就露出一条「草地到此为止」的硬边），
雾换成 `FogExp2(0xc6dae4, 0.016)`——17m 约 7%、45m 过半、90m 基本吃掉。

植被改成三层，共用一份 `leafMat`、各一个 `InstancedMesh`（含树干共 4 个 draw call）：

| 层 | 位置 | 尺寸 | 颜色 |
| --- | --- | --- | --- |
| 矮灌 | 12–26m 一圈（西侧跳过） | 0.5–1.1m，压扁 | `0.082t / 0.104t / 0.070t` |
| 灌丛 | 25–42m，132 团重叠 | 1.2–3.2m | 比树冠更暗一档 |
| 乔木 | 96 棵 × 5 团树冠，30–62m 两圈 | 高 3.4–7.6m | 每棵 `tone` 单独抖，冠内上下再分明暗 |
| 远山脊 | 76–96m，30 个大丘 | 宽 16–32m、高 4.5–11m | `0.3 / 0.355 / 0.325` 灰绿 |

第二层（灌丛）是专门补出来的：没有它，树冠底下是一条**透亮的草地缝**，
那排树冠立刻变成「浮在空中的棉花球」。真实树带的基部是不透光的。

草地本身还加了一层**顶点色低频斑驳**（`lawnMottle()`，两段值噪声叠在 `color` 属性上）：
140m 见方的一整块，只靠 2m 一循环的贴图，中景会读成一整块均匀的绿绒布。
顶点色不受 `repeat` 影响，正好补这个尺度。

### 5. 镜头感：只用 DOM，只用得起暗角和颗粒

- `.lens`：径向暗角 `rgba(26,33,30,.26)` + 顶端一点暖调，把注意力收到中心。
- `.lens::after`：`feTurbulence` 生成的 140px 噪点，`opacity .05` + `mix-blend-mode: overlay`，
  压掉大面积渐变上的色带。
- 光照：`toneMappingExposure 0.80`、太阳 `0xfff0d6 / 2.38 / (17, 17.5, 12.5)`（仰角约 39°）、
  `hemi 0.48`、`fill 0.22`；阴影 `4096`（窄于 900px 退回 2048）。

**浅景深试过，没留。** `backdrop-filter: blur()` 确实能糊掉背后的 WebGL 画布（单独做了最小用例，
右半边盖一层 blur(8px)，条纹确实糊了），但只要给它加 `mask-image` 做「中间实、四周虚」的渐变遮罩，
Chromium 就整层不绘制；把遮罩挪到父级、blur 留在子级也一样失效（父级有 mask 时，
子级的 backdrop 根被截在父级内部，没有可模糊的内容）。剩下的选择要么是全屏统一虚化（把主体也糊掉，
还要多一次全屏合成），要么上 EffectComposer——不引。所以景深这块明确放弃。

### 6. 机位

`ring` 从「西南 3/4 + pitch 20」改成**正面**：`[1.8, 1.5, 0] / r 10.2 / yaw -90 / pitch 14`。
yaw -90 就是「从牌坊往里看」那条视线，也正好是围绳修好之后最耐看的角度：
三道绳各自横平、台面透视收进去、人像站在台下抬头看。
`desk` 不动——那个角度是唯一能让「报名处」匾额正对镜头的机位。

1. **别用缩略图判断曝光。** 同一张 1440×900 的图，预览按 0.58 缩和按 0.44 缩，看起来的明暗能差一档，
   我一度以为加了叠层把画面压暗了。最后写 `cdp-stats.mjs`，在浏览器里把图画进 canvas 算直方图——
   两版平均亮度 0.549 和 0.553，根本没变。
2. **`InstancedMesh` 的 `instanceColor` 是逐实例乘上去的色值。** 想要「同一份材质、几种不同的绿」，

3. **绳子的辨识度靠下垂和分色，不靠粗。** 0.045 半径在台前三米看是一根水管；

## 第六轮：让材质经得起近看（2026-10-22）

第五轮是「退开五米像不像照片」，这一轮是「走上去三步还站不站得住」。
拉近之后三个问题特别刺眼：铺装是**画了格子的纸**（缝在法线上是平的）、
木材是**一块刷了漆的板**（法线强度 0.035、程序化木纹 alpha 2.5%，都等于没画）、
台面帆布**走样成一片竖条**。共同点不是"缺细节"，是**数量级错了**。

### 1. 铺装：板缝真的凹下去

原来的法线挂的是仓库里的 `stone-normal.jpg`——那是石块表面的起伏，
**缝本身还是平的**，于是地面像印了格子的纸。改成程序化：

```
pavingNormal() → heightToNormal(512, height, 0.005)
```

高度场和底色用**同一张网格**（4×4、奇数行错半块、缝宽 2.6/1024、倒角 7/1024）：

- 缝底 0、板面 1、中间 smoothstep 过渡；
- **每块板的倒角宽度单独抖**（`0.6 + 0.8·hash(col,row)`）——倒角一样宽的时候，整片地面像挤出来的塑料件；
- 板面再叠两个互调的正弦当微起伏，保证首尾可平铺。

`repeat` 必须和底色完全一致，否则缝会错位；纹理共享、每块地面克隆一份句柄。
顺带删掉了 `pavingMats` 那条异步链路（原本专门给铺装挂 stone-normal）。

### 2. 石材与木材：先把强度量出来再调

写了 `_shots/cdp-normstrength.mjs` 量贴图的"劲道"（法线 RG 通道偏离 128 的均值/峰值）：

| 贴图 | 平均偏离 | 峰值 |
| --- | --- | --- |
| wood-normal | 0.027 | 0.21 |
| stone-normal | 0.027 | 0.48 |
| brick-normal | 0.083 | 0.94 |

wood 的峰值只有 21%，原先给的 `normalScale: 0.035` 相当于把 21% 再乘 0.035 = **0.7%**，
肉眼当然看不见。改成：

- `oak_light / oak_flat`：`0.035 → 1.3`
- `stone_light / stone_light_in`：新挂 stone-normal，`1.2`；用 `skipColor + skipRough`
  保证自画的细石纹底色和噪声粗糙度不被照片贴图顶掉

**木材还有另一半问题在底色**：程序化木纹的 alpha 只有 `0.025 + 0.028`，本身画得比雾还淡。
现在是 `(0.045 + 0.10) × (深纹再加 1.8 倍)`，间距从「均匀 1.2~5px」改成
`1.0 + rand^1.8 × 16`（大半挨得很近、偶尔岔开一道），每道纹理的摆动幅度与周期逐个随机，
另加三条大尺度色带和三处节疤同心椭圆。等距等深的正弦是"拉丝金属"，不是木头。

### 3. 台面帆布：频率要和屏幕分辨率对上

`weaveNormal()` 原来是 48 个循环 + 台面重复 48 次——一格 **3mm**。
投影到屏幕上是亚像素，结果不是"看不见"，而是**走样成一片竖条纹**。
第一次改到 36 次重复（1.7cm）又踩了另一个坑：十米外正好落在奈奎斯特线上，
整块台面织出一层规则方格，像铺了张坐标纸。

最终 12 个循环（256 图里 21px 一格，采样够密）+ 重复 22 次 = **一格 2.8cm**，
`normalScale 0.95 → 0.55`。再补 5200 个织点（albedo 层面，随机所以不结网）
和一圈中心踩踏渐变（只给 10%，要的是"用过"不是"旧"）。

### 4. 植被：别再是正球

`lumpySphereGeo(r, wSeg, hSeg, amp, seed)`：顶点沿法线方向按三组正弦伸缩 ±20~26%，再重算法线。
正球的轮廓是圆弧拼圆弧，堆几团远看还是"绿气球"——问题不在面数，在轮廓本身太规矩。
经纬线接缝与两极是重合顶点、位移相同，不会裂开。矮灌用 0.26、树冠 0.2、远山脊 0.16。

### 5. 光：阴影偏冷，受光偏暖

真实场景的阴影里只有天光，所以背光面偏蓝；地面反弹上来的是暖的。
`HemisphereLight(0xdfeaf2 → 0xbfd6f2, 0x6f7564 → 0x7d7159, 0.44 → 0.78)`，
同时把 `environmentIntensity 0.5 → 0.35`（环境图是中性灰蓝，它占得越少，
"蓝阴影 / 暖受光"的分离越明显）、太阳 `2.38 → 2.55` 补回余弦损失。
实测平均亮度几乎不动（0.558 → 0.544），但直方图两端各多出 1~2 个百分点——对比度是靠分离拿到的，不是靠压曝光。

### 6. 机位：报名处换个角度

围绳修好之后，`desk` 原来的机位（yaw -136 / r 5.4）正好贴着擂台东侧那道绳：
一根 6cm 的绳从画面底角斜着切过整个画面，把柜台下沿挡住。
退到擂台外的东北、`yaw -150 / r 4.8 / pitch 12`，绳退出画面，匾额仍正对镜头。

## 第七轮：角落里的彩蛋（2026-10-22）

擂台西南角那片空铺装上压了一张对折的草稿纸，走近按 E 捡起来，面板上给出纸上的那句话。
**一次性的、纯本地的**：不写服务端、不进排行榜，刷新页面回到原地。

### 1. 位置是被动线定的，不是被坐标定的

人从西侧围栏缺口进来，主路在 `z ∈ [-2.25, 2.25]`。纸条放在 `(-5.0, 2.85)`——路缘石南侧 0.6m：

- 走在路上扫一眼就在余光里，但要专门拐半步才够得着（判定半径 2.0m，站在路中线上正好差一点）；
- 往西 `x < -8` 是围栏，往东 `x > -3` 是台阶和看台，只有这一段是纯空地；
- 高度 `0.0235`，铺装面 `0.02`——纸最低点离地 0.7mm，不 z-fighting，也不像浮着。

### 2. 一张"放"在地上的纸，靠三件事

不是一张平贴的白片。`PlaneGeometry(0.13, 0.175, 4, 6)` 按顶点推高度，再 `computeVertexNormals()`：

- **中缝**：`0.008 × (1 - |x| / halfW)`，抬成一道很浅的"帐篷"，两半受光不一样；
- **翘角**：只有 +Y 一侧抬 `0.004`，暗示它是从手里滑下去的；
- **波**：两道 1mm 级的正弦，纯粹为了破掉平板的高光。

第一版折 1.4cm、波 3.5mm，边缘起伏一圈，读成"揉过的纸团压平"——**纸条的褶皱是毫米级的**，不是厘米级的。
旁边再压一片 `撕下来的角`（0.046 × 0.062），两张一起才像"掉在这儿的"，不像贴了一张便签。

### 3. 接地阴影差点白画

`contactShadow()` 复用场地上所有小物件的径向渐变贴片，但它**只在中心 20% 半径内是实心的**（0.66 → 0.30 → 0）。
按纸的 1.7 倍铺，实心部分整片被纸盖住，露在外面的只剩 alpha 接近 0 的尾巴——等于没画，纸读成浮在半空。
铺到 4.5 倍（0.58 × 0.68）后，芯的边缘正好落在纸边，才有"纸压着地"的那一圈。
`y` 压在 `0.0207`（纸最低点）与 `0.02`（铺装面）之间，1mm 的缝。

### 4. 两个坐标系上的错

1. **`rotY` 会把平放的面立起来。** 撕角那块面已经 `rotX: -PI/2` 放平了，再给 `rotY: 0.9` 是绕世界竖直轴转，
   渲染出来是一片悬空的纸板。要在面内旋转得用 `rotZ`——rotX 之后局部 Z 就是世界 Y。
2. **相机仰角不是状态的一部分。** 漫游模式下 `applyWalk()` 只在按方向键时才跑，
   所以静止时直接改 `camera.position / rotation` 不会被覆盖，验收脚本就靠这一点摆特写机位。

### 5. 面板：把那句话摆在一张纸上

`#feature-dialog` 里加一个 `.note-slip`：米色底、左侧装订红线、`repeating-linear-gradient` 打的横格，
字体走 `Kaiti SC / KaiTi / Songti SC`，`transform: rotate(-.5deg)`。
**行高必须等于格线周期（28px）**，差 1px 就变成"文字压在线上"，比不画格线还难看。
纸上的字用 `textContent` 灌进 `.note-text`，不拼进 `innerHTML`——内容来自模块常量，但没必要留注入口。

## 第八轮：漫游做成真正的第一人称（2026-10-22）

原来的"漫游"其实只是**把人眼贴在 1.65m 高度上平移**：视线高度恒定、按下立刻满速、松开立刻停、
冲刺时视野也不动。走起来像一台滑轨车，不像人。

这一轮把三件事拆开做：**位移**（`state.pos` + 一阶惯性）、**姿态**（`RIG` 的步态偏移）、
**镜头**（漫游专用视野 + 冲刺时拉开）。三件都只改相机和速度，`state.pos` 仍然是脚下那个点——
碰撞、交互判定、位置名全部按它算，头一晃判定就跟着抖的话，站在纸条边缘会一直闪提示。

### 1. 视野：检视用长焦，漫游用广角

检视机位是 `2·atan(12/35) ≈ 37.9°`（垂直）的长焦，那是拍照片的镜头：透视收得紧，移动看起来慢。
第一人称要有"身在其中"的开阔感，所以漫游单独一档 `46°`，冲刺按**速度超出步行上限的比例**
连续插到 `55°`——不是"按没按 Shift"，撞墙时按住 Shift 不会把画面顶开。
进出漫游时用 `dt * 4.5` 的指数插值，0.5 秒完成，像一次推镜。

### 2. 步态：三件事同时发生

| 层 | 做法 | 幅度 |
| --- | --- | --- |
| 重心起伏 | `sin(2·phase)`，一个步幅落两次脚，所以垂直频率是步频的两倍 | 16mm |
| 骨盆左右摆 | `sin(phase)`，沿**屏幕右方向**加（`right = (cos yaw, −sin yaw)`） | 9mm |
| 滚转 | `sin(phase)` + 侧移量 | 0.4°，侧移再叠 0.0042 rad/(m/s) |
| 呼吸 | `sin(breath)`，4.2 秒一轮，走起来自动让位给步态 | 3.5mm + 0.09° |

**相位按走过的距离推进**（`phase += speed / stride`），不按时间：按时间推的话，速度一变相位就跳，
慢走时脚在打滑、快走时又跟不上。步幅随速度变长（`1.45 + 0.24v`），
4.2 m/s 对应 1.66 个步幅/秒 = **3.3 步/秒**（慢跑），6.6 m/s 是 4.2 步/秒。
先前用 `1.2 + 0.2v`，同样速度下顶到 4.1 步/秒，快得像赶地铁。

横向摆幅必须沿"屏幕右"加。直接加在 `x` 上的话，面朝 +X 时横摆会变成前后摆——这一点是写完才想明白的。

### 3. 惯性：起停都不是瞬间的

位移从"每帧直接加 `speed*dt`"改成目标速度 + 一阶趋近（`k = 1 − exp(−rate·dt)`，起步 10、刹车 13）。
指数形式的好处是**和帧率无关**：60Hz 和 144Hz 的起步手感一致，写成 `lerp(a, b, 0.2)` 就会差一截。
实测松手 100ms 掉到 1.1 m/s、200ms 归零。

### 4. 鼠标锁定：只在顶层页面申请

真实第一人称是"鼠标一动视线就动"，不用按住拖动。所以漫游里点一下画面申请 Pointer Lock。
但 **Pointer Lock 需要父级 `allow="pointer-lock"`**，预览面板是 iframe，申请必被拒——
在预览里点一下画面就弹"不允许锁定"是纯噪音。所以 `window.self === window.top` 才申请，
被拒也只提示一次、不重试，拖动转向始终可用（两种操作并存，不互斥）。

锁定状态下按 Esc 由浏览器解锁，`keydown` 不再派发，所以那一次 Esc 不会退出漫游、第二次才退，
和所有第一人称游戏一致。`setView()` 里会主动 `exitPointerLock()`。

### 5. 副作用：验收脚本要冻相机

漫游里 `applyWalk()` 现在**每帧都跑**（步态偏移是连续量，靠"有事才更新"会漏帧）。
之前那批脚本靠在静止时直接改 `camera.position / rotation` 摆特写机位，现在会被立刻覆盖，
所以 `__arena` 加了 `freezeCam(true)`：冻住之后 `applyWalk()` 直接 return。
`cdp-note*` 已经改成"冻 → 摆机位 → 拍 → 解冻"。

| 视野 | 检视 `37.85°` → 漫游 `45.88°`（→46）→ 冲刺 `55.0°` → 退出后回 `37.88°` |
| 速度 | 步行峰值 `4.20`，冲刺峰值 `6.60`；松手 100ms 后 `1.09`、200ms 后 `0.003` |

## 第九轮：柱子（2026-10-22，第二稿）

场地里"柱子"有三类：擂台四角立柱、牌坊两根门柱、围栏立杆。前两类站在人眼高度、
天天被盯着看；第三类（0.08 的栏杆立杆）只是围栏节点，保持原样。

这一轮改过两版。**第一版**另起了一套七段式（两级石座 → 金属法兰 → 柱身下段 / 喉箍 /
上段 → 石帽，牌坊柱再挂一道柱头铜箍），单看是比原来的一根方管好看，但站到接缝上
两个板块一起看，问题立刻出来：**广场亭廊柱是"石础 + 涂装柱身 + 石柱头箍"三段，
竞技场是七段，两米开外并排，一眼就不是一个场子里的东西。**

于是**第二版把第一版整条推翻**，改成"按柱径等比重算广场那套件"。

### 真相在 `social-district.js` 的 `buildPavilion()`

广场亭廊柱四件事，一件不多：

```js
add(boxGeo(0.36, 0.018, 0.36), metal_dark, ...);                 // 地面深色垫板（1.64×）
add(beveledBoxGeometry(0.29, 0.12, 0.29, 0.014, 1), stone, ...); // 石柱础（1.32×）
add(beveledBoxGeometry(0.22, colH - .12, 0.22, 0.01, 1), painted); // 涂装柱身（1.0×）
add(beveledBoxGeometry(0.30, 0.09, 0.30, 0.008, 1), stone, ...); // 石柱头箍（1.36×）
```

关键在最后一件：柱头是**套箍**，不是压在柱顶上的帽子——柱身一直伸到梁底，
石箍包住最上面 9cm，梁坐在箍上。原来竞技场是"柱身 + 一块盖板"，这条比例关系从头就没有。

### 一套尺寸，两个柱径

`column(x, z, baseY, size, top, capGap)`，内部只用一个系数 `k = size / 0.22`：

| 段 | 尺寸 | 材质 |
| --- | --- | --- |
| 垫板 | `0.36k × 0.018 × 0.36k` | `metal_dark`（不投影） |
| 柱础 | `0.29k × 0.12k × 0.29k`，倒角 0.014 | `stone_light` |
| 柱身 | `size × (top − baseY − 0.12k) × size`，倒角 0.010 | `metal_dark` |
| 柱头箍 | `0.30k × 0.09k × 0.30k`，倒角 0.008 | `stone_light` |

- **牌坊柱 `size = 0.22` → `k = 1`**：和亭廊柱**一模一样**，只是更高（柱顶 3.00 = 梁底）。
- **擂台柱 `size = 0.18` → `k = 0.82`**：同一套件的 0.82 倍。

`capGap` 是"箍顶离柱顶还有多远"：擂台柱的横梁就坐在 2.83，`gap = 0`；
牌坊的梁底在 3.00，柱顶也在 3.00，同样 `gap = 0`。这个参数留着是为了以后加檐时不改签名。

### 三处"照抄"，都是不一致会露馅的地方

1. **倒角用绝对值 0.014 / 0.010 / 0.008**，不跟着柱径缩。倒角是"这条边是块料"的唯一信号，
   按比例缩到 0.008 就退回方管了。
2. **石料用 `stone_light`（0xcfc8ba）**。两个板块里只有这一档是完全同色的；
   竞技场的 `stone_light_in` 是 0xc3bcac，比广场那档（0xd2cbbd）暗一截，接缝处并排会看出来。
3. **柱身用 `metal_dark`**，不再另起材质。第一版为了"黑板问题"造了 `post_steel`
   （0x535c50 / 0.44），单看确实比 `metal_dark` 立得住，但并排时
   **广场的柱子是黑的、竞技场的柱子是灰绿的**——风格统一优先于单点好看。这一版把
   `post_steel` 与 `brass` 一起删掉了（`MATERIAL_SPEC` 与 `ROUGH_NOISE_IDS` 同步清理）。

### 一处必须留的差异

擂台柱的护角垫（`0.245 × 0.80`，`canvas_olive` + 两道米白束带）比柱础还宽，
而且下沿离柱础顶只有 5cm，所以**柱础在大部分机位里是"半步就被垫子接走"的**。
这不是没做柱础——是擂台的柱子本来就要裹垫子。反过来，正因为有这块垫子，
柱础和柱头箍才必须做足，不然整根柱子只剩"一根杆 + 一个桶"。

## 第十轮：把三件"走近了看"的细节做实（2026-10-22）

这一轮没有动场地结构，只补三处**人一定会凑近看**的物件：开赛锣、锣槌、报名处台面。
判断标准是"退到正常观看距离还读不读得出来"，不是"多加几个面"。

### 1. 开赛锣：一块平盘读不成铜锣

原来的锣是一个厚 3.5cm 的**平**圆柱，正面叠了几片更薄的圆盘当细节。问题不在细节数量，
在**正面是平的**：平面在光下没有明暗梯度，无论怎么调材质（这次也顺手把凸脐压扁、
车削纹贴上球面），正对时都是一块棕色圆板。另一个硬伤是吊绳从锣心穿下去——
物理上没法敲，画面上等于把锣面切成两半。

改法：

| 部件 | 做法 |
| --- | --- |
| 锣面 | 半径 1.1m 的**浅球冠**（开口半角 `asin(0.335/1.1)`，鼓起 5.4cm） |
| 卷边 | `TorusGeometry(0.332, 0.014)`，轴沿 X，比锣径外凸 9mm |
| 车削纹 | 一道 `TorusGeometry(0.255, 0.0045)`，贴在球面上（不是浮在同一平面） |
| 中心凸脐 | 球 `r=0.068` 沿轴向压到 0.34——第一版 0.078/0.5 是一只门把手 |
| 悬挂 | 绳吊到**上缘**（长度 `ropeLen − r`），加一只吊环，锣心高度不变、摆轴不变 |

球冠用 `SphereGeometry(1.1, 56, 16, 0, 2π, 0, θ)` 再 `rotZ = −π/2` 把极点转到 +X。
分段不能省到 44×10：那档在左上会出现一条折痕状的高光。

### 2. 锣槌：门洞这一片原来只有一口悬空的锣

没有"谁敲它"的痕迹。补一只槌，而且必须是**放下的**——挂在柱上就成了装饰。

- 头：`0.10 × 0.17` 的木圆柱（轴向 X）+ 一端 12mm 深色箍。
- 柄：`0.45` 长、`0.030 → 0.036` 的锥形圆柱，`rotZ = 0.20`（11.5°）。
  角度不是拍脑袋：柄底接槌头、柄顶正好碰到柱东面 `x = G.x + 0.11`，两点反算。
- **z 必须落在柱子的厚度里**（柱心 `−2.00`、半宽 0.11）。第一版放在 `−1.86`，
  看着"挨着柱子"，其实是立在柱子**旁边**，从东侧看柄顶悬空，读成一根自己站着的木棍。

### 3. 报名处：0.66 × 1.7 的台面只有一块立牌

一件家具上有没有"用过"的痕迹，比它自身分段做得细不细更决定可信度。

| 物件 | 位置 / 尺寸 |
| --- | --- |
| 登记簿 | 台面南端（`z + 0.68`）：深色封皮 `0.36 × 0.27`，摊开两页各 `0.142 × 0.232`、向外抬 4° |
| 铅笔 | 横搭在**中缝**上（`0.155` 长、Ø10mm），这是书唯一放得住笔的位置 |
| 叫号铜铃 | 台面北端（`z − 0.68`）：底座 + 半球（`scale.y 0.86`）+ 柄 + 顶珠，`bronze` |
| 柜门拉手 | 两扇门各一条 `0.026 × 0.024 × 0.17` 的横杆 |
| 空图标 | `<link rel="icon" href="data:,">`，把验收里那条"无关的 favicon 404"消掉 |

位置都避开中间的立牌（立牌占 `z ± 0.6`），放在两端各 ±0.68 的窄条里。
台面进深只有 0.66，所以登记簿沿 X 摆、不能顺着台子放。

### 踩过的四个坑

1. **两圈车削纹读成"靶心"，也像音箱**。锣面本来是素的，只留最外一道，
   当作卷边和鼓面之间的过渡。
2. **铅笔斜放在页面上，看着是浮的**。柜台在棚子底下没有直射光，`cast:false` 又不投影，
   一根 Ø14mm 的细棍悬在纸上方 2mm，在 0.8m 的机位上就是"浮"。改成横搭中缝，
   顺便把直径从 Ø14 收到 Ø10。
3. **深灰钢拉手在这个角度反射的是暗环境**，两条把手读成贴了两条黑胶带。换 `bronze`。
4. **`oak_flat` 的纹理在细圆柱上会被 UV 拉平**，柄看起来像一根塑料棒。
   这个尺度上无解（真做要单独写一套 uv），接受。

### 验收（`cdp-detail` / `cdp-entry` / `cdp-note` / `cdp-fps`）

| 检查项 | 改前 | 改后 |
| --- | --- | --- |
| 网格 | 296 | **309**（+13） |
| draw calls | 285 | **298** |
| triangles | 119 044 | **122 720** |
| 帧率（headless） | 168 / 199.5 fps | 139 / 161 fps |
| 控制台 | 0（含一条 favicon 404） | **0**（404 已消） |
| 回归 | — | 三机位、擂台 / 报名处 / 锣三个面板、纸条全流程、主站入口全绿 |

headless 的帧率每次都不一样（软件光栅），这一轮多出来的 ~3700 个三角形全在锣的球冠和
三道环上，真机上不是一个可测的量。

### 顺带说清楚：这一轮为什么没有碰"台面帆布的摩尔纹"

`sw2-canvas` 那张图里帆布远处的细格纹，一部分是**无头渲染没有各向异性过滤**造成的，
真机上 `weaveNormalTex.anisotropy = 8` 会把它压下去。在没有真机对照的情况下调
`repeat`，很可能把真机调坏，所以不动，只记录。

## 第十一轮：从"拳击台"改成"知识竞赛台"（2026-10-22）

上一版把场地做得像一张**拳击台**：三道下垂的包布围绳、柱身裹着护角垫、台心两道同心圆
加一个中心点，四个角还都挂着「擂」。单看都对，但两个问题一起出现：

1. **语汇不对**。围绳、护角垫、同心圆台标是格斗场的三个签名，和旁边的亭廊、图书馆
   （石材 + 涂装钢 + 木构 + 玻璃）不是一个体系。并排站着像两个不同工地的产品。
2. **说不清在比什么**。这块地叫「好友竞技场 / 五题定胜负」，但场上一件和"题"有关的
   东西都没有——只有一张能打的台子。

判断是：**围绳和护角垫不去掉，换什么颜色都还是拳击台。** 它们不是配色问题，是形制问题。

### 改法：围护换成建筑语言

| | 改前 | 改后 |
| --- | --- | --- |
| 围护 | 三道 Ø60mm 尼龙绳，抛物线下垂 42mm，下深 / 中橄榄 / 上米白 | **1.02m 木扶手**（0.16 宽，`oak_flat`）+ **0.52m 橄榄赛带**（0.20 高，平直） |
| 立杆 | —— | 每边两根 0.05 方管竖向栏杆 |
| 连接 | 圆柱绳扣（每柱 3 个） | 方抱箍（每柱 2 个，扶手和赛带各一） |
| 柱身 | 裹 0.245 × 0.80 橄榄护角垫 + 两道米白束带 | **干净**（护角垫整个删掉） |

两个理由，写在代码注释里也说了一遍：

- **木和涂装钢是这块校园建筑的语言**。广场亭廊是木构 + 深色涂装钢柱，图书馆是石材 + 木 +
  玻璃；绳子是这三样之外的东西。
- **下垂是"受力绳索"的读法**。围带是张紧的，必须平直。下垂 42mm 那一条弧线，
  在 10m 外就是"这是一根绳"的全部证据。

### 台心：同心圆换成八角

原来是 `RingGeometry` 两道同心圈（1.34–1.46 / 0.86–0.94）+ 一个 Ø0.52 的中心点——
这是拳击台的标准台标。现在换成**一个八角的空心环**（内 0.66 / 外 0.80，8 段）：

- 八边形读的是「令牌 / 答题卡 / 印章」，和牌坊、竖幡同族；
- 它是**空心**的，中间留给答题台和站位，不像靶心那样把视线钉死在正中。

### 答题台：这是全场最直接的一句话

两座，**南北相向**，摆在台面上。第十三轮之前选手上不了台，但那两座空着的台子照样读成
"人还没上来"，不是"这里没有比赛"——牌和灯是开着的。现在人能站上来了，台子仍是空的：
人走到旁边没有入座、没有动作，见「未完成」。

| 部件 | 尺寸 |
| --- | --- |
| 台体 | 0.54 × 0.88 × 0.58，`oak_light`（和广场的坐凳、亭廊同一档木） |
| 底座 | 0.58 × 0.04 × 0.62，`metal_dark` |
| 台面板 | 0.60 × 0.03 × 0.66，向对手一侧挑出 4cm |
| 裙板 | 0.52 × 0.055 × 0.56，`metal_dark`（台面下面一道阴影线） |
| 甲乙牌 | 0.40 × 0.28 深色板 + 0.36 × 0.24 字面，**朝西**（正对进场方向） |
| 小灯 | 杆 0.16 + Ø0.10 球，`accent_amber` + 一张加色光晕 |

**为什么沿 Z 分列而不是沿 X**：预设的「擂台正面」机位是从西侧斜看进来的，
沿 X 摆的时候两座台子正好一前一后叠成一根柱子，画面里像台心多了个怪东西。
沿 Z 摆，从西侧看就是左右两座、隔着八角区相向，一句话就读完。

**甲乙牌为什么朝西**：牌子是给围观的人认人的，对手不需要看。朝西之后，
从牌坊走过来的第一眼就是"甲 / 乙"两块牌，而不是两个木箱子的侧面。

### 四角竖幡：四张「擂」换成 数 / 英 / 语 / 综

网格数不变、成本为零（只是四张字），但一眼就把"这是比什么"说清楚了：
四角立着四科的幡、中间两块答题台。全名仍然留给牌坊匾额。

### 踩过的坑

1. **拆掉围绳之后整个台子"空了"**。第一版只留木扶手 + 赛带，从入口看过去是一块
   低台加几根细杆，比原来还没信息量。补了三样：每边两根竖向栏杆（把扶手和台面连起来）、
   赛带从 0.15 加宽到 0.20、木扶手从 0.075 加宽到 0.16。**围护必须能从 15m 外读出来**。
2. **答题台第一版沿 X 摆**，在预设机位上两座叠成一根柱子（见上）。
3. **答题台就是一个 0.54 × 0.88 的实心木箱**。加一道深色裙板（比台体窄 2cm）之后，
   才有"台面挑出来、底下一个柜子"的关系，也就是"桌子"而不是"箱子"。
4. **删干净比留下更好**。围绳没了之后，`ropeGeometry()`（抛物线下垂的管子）、
   `ropeNormal()`（麻花法线）、`rope_dark` 材质、`L.rope` 布局常量全部变成死代码，
   一起删掉；`canvas_olive` 只剩报名处的棚顶一处用途，注释同步改掉。

### 验收（`cdp-entry` / `cdp-ring2` / `cdp-seam` / `cdp-note` / `cdp-fps`）

| 检查项 | 改前 | 改后 |
| --- | --- | --- |
| 网格 | 309 | **311** |
| draw calls | 298 | **302** |
| triangles | 122 720 | **118 816**（少了围绳的 TubeGeometry） |
| 帧率（headless） | 120 / 146 fps | **123 / 156 fps** |
| 控制台 | 0 | 0 |
| 回归 | — | 三机位、擂台 / 报名处 / 锣三个面板、纸条全流程、主站入口全绿 |

**headless 帧率不能当真**：同一份构建在十分钟内测到过 `88 / 118` 和 `123 / 156` 两档
（软件光栅 + 机器负载），所以这一轮只把 `calls` / `triangles` 当数，帧率只做"没退化"的旁证。

`cdp-seam` 是这一轮新写的并排机位：`preview.html?with=social` 下站在接缝上平视，
左边是喷泉、公告栏、坐凳、灯柱，右边是竞技场——木扶手、琥珀色小灯、深色涂装钢
这三样一致之后，两块地方才像一个校园。

## 第十二轮：给擂台开一道西门（2026-10-23）

### 现象

第十一轮把围绳换成木扶手 + 赛带之后，四边**全都封着**。站在场外看，那是一圈栏杆
围着一块高出地面 0.63m 的石台：看不出从哪儿上，台心那两块答题台和八角台标也全被
关在里圈。台阶明明只修在西侧、只有那一个上台口，围护却在那儿照样拦了一道——
**台阶通向一个没有门的墙。**

### 改法

只开西侧一处，正对那两跑台阶；另三边照旧整根。

| 部件 | 处理 |
| --- | --- |
| 门洞净宽 | **3.4**，直接取 `L.step.width`（台阶宽） |
| 西侧扶手 | 1 根 6.48m → **2 段各 1.54m**（`gateSeg = postR - gateHalf`） |
| 西侧赛带 | 同上，2 段 |
| 西侧两根竖栏杆 | **不留在门洞里**（那正是要过人的地方），改到门洞两侧当门垛 |
| 门垛 | 0.09 见方 × 高 1.24（比扶手高 0.22），柱顶压 0.13 见方、25mm 厚的小柱帽 |
| 另三边 | 扶手、赛带、每边 2 根竖栏杆，一根没动 |

宽度直接绑台阶宽，是为了让**台阶两肩和门垛落在同一条线上**——站在台阶上看过去是
一个直通台面的口子，以后改台阶宽度不用再对一次尺寸。

### 一个被否掉的做法

第一版在两根门垛上架了一道 0.09 × 0.06 的木横梁当门楣，理由是「有柱有梁才像门」。
实拍否掉了：

- 擂台的主视角就是**正面站在西门外**（`PRESETS.ring`，yaw −90 正对），那道梁在
  这个机位里正好横切过台面和两块答题台，把最好的一眼挡掉；
- 围护本身只有 1.02m，架梁之后比例像闸机，不像门。

改成「门垛加高 + 收柱帽」：柱子比扶手高 0.22，顶端一个小方帽收口，视线全通。
**门靠两根立起的柱子读，不靠一道横梁读。**

### 代价与边界

- 网格 311 → **315**（西侧扶手/赛带各多一段、两根竖栏杆换成两根门垛 + 两个柱帽）；
  碰撞体仍是 20 个，交互点仍是 4 个（`arena.ring` 依旧挂台阶，半径 3.2）。
- 这一轮**门还是形制开口**：台基整块仍是碰撞盒（`arena:ring`），台阶也是（`arena:step`），
  人物走到台阶前就被挡住。真能走上去是下一轮做的（见第十三轮）。

## 第十三轮：把西门做成真能走的（2026-10-23）

第十二轮开完门之后，人站到台阶前还是被挡住——门在那儿，路是断的。这一轮把门接通。

### 三件事，缺一件都上不去

| 卡点 | 原因 | 改法 |
| --- | --- | --- |
| 台阶高度不够 | 原 2 跑、起 0.18，最高只到 **0.36**，离台面 0.63 差 **0.27** | 改 3 跑、起 0.21，**0.63 正好到台面**，最后一级和台面齐平 |
| 台基整块挡人 | `arena:ring` 是一个整盒（含台面），四面都撞 | 拆成**沿围护的四条**（宽 0.30），**门洞那一段不铺**；台阶不再单独挡人 |
| 宿主不知道台面高 | 独立页相机写死 `EYE`，hub 的 `groundAt()` 只认得教学楼那片 0.6m | 两边都加台面/台阶采样（见下） |

`0.27` 这个数不是估算：`base 0.55 + cap 0.08 = 0.63`，`0.18 × 2 = 0.36`，差的就是那一段立面。
台阶只到 0.36 的时候，它是"走到台边把面板打开"的台阶，不是"走上去"的台阶。

### 台基碰撞为什么拆成四条

台基不能整块拿掉——拿掉之后人能**从任何方向**穿过围护走进台面，因为围护本身只是网格、没有碰撞。
所以碰撞必须落在围护那条线上：

- 南 / 北：沿 X 全宽，宽 0.30，落在 z = ±(3.6 − 0.15)
- 东：沿 Z，避开两条南北条的厚度
- 西：**门洞 z ∈ ±1.7 不铺**，两侧各 1.9m 补到角上

结果是「围护的线和碰撞的线是同一条」：站在台面上走不到边缘 0.30 以内，从外面也撞不进台口。
**只有西门是通的。**

### 宿主侧的高度采样

| 宿主 | 改动 |
| --- | --- |
| 独立页 `index.html` | 新增 `arenaGroundAt(x, z)`，`applyWalk()` 的相机 y 从 `EYE + RIG.offY` 改成 `arenaGroundAt(...) + EYE + RIG.offY`；台阶按"从最外沿往东数第几跑"给高度 |
| 自测页 `preview.html` | 同样的 `arenaGroundAt()`，但**带 `?h` 参数时一分不动**——验收脚本靠它精确摆机位，不能被地面高度污染 |
| 整合版 `campus-hub` | `src/layout.js` 的 `groundAt()` 加擂台台面与台阶；`ARENA_ROOT` 常量取代 `world.js` 里写死的 `39` / `2` |

`hub` 的两个常量（`ARENA_CX` / `ARENA_TOP`）是**从 arena 的 `ARENA_LAYOUT` 抄过来的**，注释里写明了
对齐关系（ring cx 1.8 / size 7.2 / base .55 + cap .08；step 3 跑 / run .44 / rise .21）。
改 arena 的任何一个尺寸，`layout.js` 要跟着改，否则人会踩空或陷进石材。

### 验证

### 还是没做的

- 台上没有动作：没有"站定 / 准备 / 作答"的姿态，没有选手 NPC，答题仍在 DOM 面板里。

  真实脚踝会有一个 0.1 秒的抬腿，现在是"跳上去"。要顺可以做，但不属于"门通不通"。

## 第十四轮：台上有人（2026-10-23）

第十三轮把门接通了，但台上是空的：人能走上去站着，两座答题台只有牌和灯亮着、台后没人；
而且三跑台阶每级 0.21 是**阶跃**——人一帧抬 21cm，读成掉帧。这一轮补这两件事。

### 1. 台阶不再"跳"上去

| 宿主 | 改法 |
| --- | --- |
| 入口页 `index.html` | `applyWalk()` 里新增 `stepGround(dt)`：按 15/s 指数趋近 `arenaGroundAt()`，`0.21` 约 0.15 秒抬完（正好一个抬腿的时间）。带 `dt` 就是平滑，不带就是"摆到位" |
| 自测页 `preview.html` | 同样的平滑，但 **`?h` 路径一分不动**——验收脚本靠它精确摆机位 |
| 整合版 `campus-hub` | `frame()` 里的 `smoothGround` 取代原来的 `groundAt()` 直读，相机与人物脚底都用平滑值 |

两处都设了一个吸附阈值：跳变 > 1.2m（`setPose`、返回状态、传送）直接吸附。
不设的话，切机位时相机会从半空飘下来一段。

**单帧最大抬升**（CDP `requestAnimationFrame` 逐帧采样 camera.y）：

| | 改前 | 改后 |
| --- | --- | --- |
| 入口页 | 0.21（一级台阶一帧） | **0.0466 / 0.0415**（两次采样） |
| 整合版 | 0.21 | **0.0262 / 0.0854** |

整合版那个 0.0854 是帧间隔不均时的单帧值（400 帧里最长的一帧），总量仍是 0.63。
两台机器上"抬完 0.63 用的时间"都是 0.15~0.25 秒，和步频对得上。

### 2. 台上真的有人了

两个**作答位**，和两座答题台一一对应（`arena.stage.jia` / `.yi`）：

- 站位离开台心 2.14m = 1.62（台位）+ 0.26（台面挑边）+ 0.26（人贴住台面）。
  前两段是量出来的（台面沿 Z 铺到 1.88），第三段是"手能扶到台面"。
- 台面上画一圈三面米白**站位线**，开口朝答题台——人从八角区走过来正好站进缺口。
  用 `rope_cream` 不用橄榄色：橄榄色是这块场地的识别色，再画一圈会和赛线、色带抢。
- 交互锚点放在**站位**上，不放答题台本体。台子 0.88 高、占着台面，锚点落在台子中心时
  人在台上走动会先命中台子，提示会变成"这有个柜子"。
- 两个交互点都只**报位置和动作**：`{kind:'pose', station, seat, stand, yaw, clip}`。
  人物是宿主的（VRM/GLB 那套加载链只在 campus-hub 的 bundle 里），竞技场模块不塞 4MB 资源进去。

### 3. 宿主怎么接

| 宿主 | 就位之后 |
| --- | --- |
| 整合版 `campus-hub` | 人摆到站位、`wave` 举手一次、锁住移动；**对手 NPC**（`src/arena-opponent.js`，prototype 连帽衫学生）换到对面那座台，也举一次手。E 重复举手，Esc 起身 |
| 入口页 `index.html` | 第一人称没有身体，只能把人摆到站位、朝向对面台、锁住移动；E 是相机抬 6cm 的一次性"举手"，Esc 解开 |
| 自测页 `preview.html` | 只吃 `update(dt, player)` 的台面判定，不接就位 |

对手 NPC 是**宿主侧**的东西，不是板块的：他站乙位候场，玩家去甲位他就去乙位，反之亦然。
用 `prototype` 变体（GLB 连帽衫学生）而不是默认的 anime VRM——台上两个人穿得一样
会读成"复制粘贴"，认不出哪个是对手。加载失败只 warn 一次，不阻断整个校园。

### 4. 台心八角会亮

`M.stage_mark` 是**独立一份材质**（原来那块八角地贴和赛带、色带、幡共用 `arena_olive`，
共用的话人一站上台，整块场地的色带会一起发光）。
`update(dt, player)` 收玩家世界坐标，用 root 的逆矩阵换成本地坐标判定"在不在台面上"，
`stageOn` 按 5/s 趋近，亮起后再叠 ±0.10 的呼吸。`get stage()` 给验收脚本读，不参与业务判定。

`player` 是可选参数：`preview.html` 不改也能跑，只是不亮。

### 踩到的坑

- **坐标系混了**：`arena.stage.*` 报的 `stand` 是**板块局部的**（`arena-district.js` 的 root 局部），
  而 hub 的 `state.x/z` 是**世界坐标**，两者差一个 `ARENA_ROOT` 的偏移。第一版直接写进 state，
  人当场被瞬移到庭院水池边（`x 1.8 / z 2.14` 恰好落在校园原点附近）——截图里人物站在水池旁举手，

- **独立页按 E 弹出了开赛锣的面板**：`interact()` 里没给 `arena.answer` 分支，落到了最后那个

## 第十五轮：两个真人一起答（2026-10-23）

第十四轮交付的「候场对手」是个本地 NPC——玩家去甲位，他就走到乙位站定。
**那不是用户要的**：他要的是两个真实玩家同场，互相看得见。这一轮把它换掉。

### 分工：表现归 3D，规则归服务端

| 谁 | 负责 |
|---|---|
| `server/community` | 谁发起挑战、答几题、答对几道、谁已交卷、比分。唯一真相 |
| `server/campus/presence.js` | 谁站在哪个位、在做什么动作。一次性表现，刷新即失 |
| `campus-hub/src/duel.js` | 把上面两件事接到 3D：连 socket、进出位、转发动作 |
| `campus-hub/src/arena-opponent.js` | 只画「对手那个真人」的化身，不自己走位 |

判分/计时/交卷**全部不进 3D**。擂台现场丢了顶多是两个人看不见对方，刷新就回来。

### 事件（都在 `/community` 这条既有连接上，不另开 namespace）

`duel:enter`(ack) / `duel:seats`（自己收全表）/ `duel:seat`（别人收增量）/
`duel:state`（挑战变化广播）/ `duel:act` / `duel:leave` / `duel:left`。

### 「房」什么时候存在

**挑战创建时 `status` 就已经是 `active` 了**——那只是邀请发出去了，台上还没人。
这一轮把建房条件改成「至少一个成员 `sessions[uid].startedAt` 有值」，也就是
**真的有人点了「开始作答」**。所以邀请阶段去按 E，服务端回「这场挑战不在进行中」，
台上不会出现一个空擂台让人以为对面正在准备。

### 一个位只能一个人

服务端在 `room.seats` 里按 `station` 去重，撞位直接回「这个作答位已经有人了」。
客户端 `enter()` 的返回值分成四种处境，提示文案一一对应，不合并成一句「正在等」：

| 返回 | 提示 |
|---|---|
| `ok:false` | 服务端拒了（位子被占 / 不是你的挑战） |
| `online:false` + 有 challenge | 正在连接擂台现场 |
| `online:false` + 无 challenge | 还没有进行中的挑战 |
| `online:true` + `peer` | 对面是 X（X 位） |
| `online:true` 无 `peer` | 已在甲/乙位，正在等搭子就位 |

### 踩过的坑

- **`duel:enter` 一直回「挑战或作答位无效」**：`station()` 收的是 `{station:'jia'}` 这样的对象
  （和 `campus:join` 的 `pose` 同一套写法），而 handler 传的是 `body.station` 那个字符串。
  改成传 `body` 整包。这个 bug 在浏览器里也是同样的症状。
- **一个账号只能有一条同场连接**：后连的会把前一条顶掉（`campus:join` 的 replace 分支）。
  写测试时每个 case 重新 `connect()` 会让上一个 case 的 socket 静默失效，
  后面 `once(sa,'duel:seat')` 永远等不到 → 整个测试挂死。改成 `before` 里连一次、全 case 复用。
- **`once()` 没有超时**：事件不来就永久挂住，`node --test` 也不会自己报。
  测试里统一换成带超时的 `wait()`。

### 第二轮修复：**`peers` 一直是 `null`、「正在连接擂台现场」永不结束**（2026-10-24）

上一轮的服务端单测（直接连 socket）全绿，但**在真实浏览器里两个人谁也离不开自己的位**：
`snapshot().duel.status` 卡在 `connecting`、`peer` 一直是 `null`、`opponent.visible=false`。
查下来是三个独立的问题叠在一起，只有真机（两个隔离的浏览器进程）才暴露得出来。

#### 坑 1：`enter()` 没等握手完成就去 join

`await connect()` 只保证 `io(...)` 这个**客户端对象**建好了；它内部的握手是异步的，
回来时 `socket.connected` 往往还是 `false`。接着 `ensureJoined()` → `join()` 第一句
`if (!socket?.connected) return false`，**静默**返回失败，`joined` 仍为 `false`，
于是 `enter()` 走了 `if (!joined) → status='connecting'` 这条提前返回分支。

界面看起来像"正在连"，实际上连接半秒后就好了，只是没有人再回来补这一步。

改法：新增 `waitConnected(ms)`，显式等 `connect` 事件（已连上直接过）；
`enter()` 和 `join()` 都先经它，`join()` 里那句静默 `return false` 也去掉——
"还没连上"和"连接坏了"本来就是两件事，不能都返回 `false`。

#### 坑 2：座位空了就删房 → 同账号第二条连接一来，房就没了

`duelLeave()` 和 `duel:leave` handler 里都有 `if(!room.seats.size) rooms.delete(id)`。
**房间的生命周期属于挑战，不属于座位**：挑战一开始就该有房（有人在答、另一个随时能坐进来），
`seats=0` 是常态。

真实场景：整合版校园里，`presence.js` 会为漫游同场开一条 socket，`duel.js` 自己再开一条。
第二条 `campus:join` 进来时走 replace 分支 → `leave(旧socket)` → `duelLeave()`，
**第一件事就是把刚建好的空房删掉**，紧接着 `duel:enter` 一律回「这场挑战不在进行中」。
台上明明有比赛，两个人谁也坐不上。

改法：删房只由「挑战失效」决定。抽出唯一的判定

```js
const isLive = (c) => c.status==='active' && (!c.expiresAt || c.expiresAt>Date.now()) && started(c);
```

`duelLeave` / `duel:leave` 后只调用 `syncChallenges()` 扫一遍**已经结束/过期**的房。

#### 坑 3：`duel:leave` 不回 ack

客户端起身之后没有任何回音，只能靠猜或干等超时（测试里就是这么暴露的）。
现在 `duel:leave` 也带 ack，回 `{ok:true,station:null}`。

#### 三个坑为什么只有浏览器能发现

| 坑 | 服务端单测 | 浏览器 |
|---|---|---|
| 1 握手时序 | 看不到——测试是 `await once(s,'connect')` 之后才发事件 | 必现：`io()` 之后直接 `enter()` |
| 2 空房被删 | 看不到——测试里每个账号只连**一条** socket | 必现：`presence.js` + `duel.js` 各一条 |
| 3 缺 ack | 看不到——测试没对 `duel:leave` 取 ack | 表现成"起身后状态不更新" |

坑 2 是这轮最值钱的一条：**"座位空了"不等于"比赛结束了"**。
把这两个概念混在一个 `if` 里，本地单 socket 永远测不出来，因为它需要"同一个 uid 的第二条连接"。

### 验证

- `server/test/campus-duel.test.js` **6 个 case 全绿**：邀请阶段无房 → 非成员不能就位 →

## 未完成 / 明确不做

- **台上是真人，但只同步"在场"**：第十五轮起甲乙两个位坐的是**真实玩家**（服务端 `duel:*` 事件），
  没有 NPC 也没有机器人。但同步的只是"谁在哪个位、在做什么动作"——
  谁作答、答对没有、比分多少，仍归服务端与 DOM 面板，3D 侧不写第二套状态。
  台上没有观众、没有对打动画，也没有 3D 里的计时器。
- **对手化身的资源挂在 hub**：`js/features/campus-hub/src/arena-opponent.js` 只在 `campus-hub` 里渲染；
  独立入口页（第一人称）复用的是 `campus-hub/src/duel.js` 的现场层，但不画对手的 GLB 模型。
  竞技场模块本身只报站位与动作，不带人物资源。
- **对战牌没有实时比分**：只有场地标识。挑战的发起与判分都在服务端，3D 侧不显示假战绩。
- **锣只响不判**：本地计数 + 2.4 秒阻尼摆动，不写服务端、不发 Socket 事件。
- **树被移除了**：第一版在场地内放了树，从并排机位读过去像「擂台里有几个绿球」。绿化交给旁边的社交广场，本板块只留草坪。
- **只有白天**：4 盏灯笼只有 `emissiveIntensity` 的呼吸（0.26±0.08）加一张加色 Sprite 灯晕供观感，
  没有实际照明（不加 PointLight：每盏灯都会让全场景材质的着色成本上升）、没有夜景。
  台心那圈八角是**贴片自发光**，同样不投光，只把台面点亮。
- **答题与复盘不在这一页**：需要数学排版，仍回主站。这一页只做「读列表 / 发起 / 开始 / 取消 / 处理邀请」这五个不需要排版动作。
- **没有实时推送**：主站靠 Socket + 15 秒兜底轮询，这一页只在打开面板那一刻取一次。看完关掉再开才会刷新。
- **没有后处理，也就没有浅景深 / SSAO / Bloom**：`vendor/three/` 里没有 `EffectComposer`，不为了一个景深去引整条后处理链。
  边缘虚化用 `backdrop-filter` 试过，被 `mask-image` 一挡就整层不绘制（详见第五轮）。现在的「镜头感」只有暗角 + 胶片颗粒。
- **植被是程序化低模**：三层植被靠 `InstancedMesh` + 顶点抖动拼出轮廓，近看仍然是球。
  真要照片级得换带 alpha 的广告牌树木贴图，那是另一套资源管线，不在本板块范围内。
- **没在物理手机上验过**：手势与布局是 CDP 触摸事件 + 两档视口尺寸验的，真机的滚动惯性、地址栏收放还没跑。
