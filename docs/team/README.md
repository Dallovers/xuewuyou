## 工作顺序

1. **先对齐**：A、C 确认[续学接口草案](practice-session-contract.md)；B 固定页面/组件规范；C 给你确认后的素材清单和落位参考。
2. **并行开发**：A 优先稳定登录、同步和持久化；B 先完成首页、题目页两个样板，再覆盖全站；C 先做无新图片也能运行的续学与地图交互。你先生成学院和自习馆两张试图。
3. **集中联调**：接口与真实数据打通后接入全部建筑，检查自习→练习→草稿/错题→复习→报告的链路。
4. **冻结验收**：停止加功能，按[验收清单](acceptance.md)交叉测试、修完已知问题，再由 A 发布，你最后按队友的实际设备复查。

没有给定比赛截止时间，因此以上按阶段安排，不假设具体交付日期。新增功能先交付断点续学；资料书签等候选需求在本轮稳定验收后再排期。

## 文件与合并边界

| 唯一负责人 | 负责文件 |
|---|---|
| A | `server/**`、`js/api.js`、`js/deploy-config.js`、部署文件、`.github/workflows/**`、`tests/e2e/**` |
| B | `index.html`、`css/**`、`js/app.js`、`js/ux.js`、`js/campus-interactions.js`、品牌/字体/图标规范 |
| C | `js/atlas.js`、`js/atlas-assets.js`、`js/campus-registry.js`、功能前端脚本、新增 `js/practice-resume.js`、地图素材清单 |
| 你交付、C 接入 | 地图建筑原图与 `vendor/atlas-art/` 的发布素材 |

- 三人分别使用 `team/backend`、`team/frontend`、`team/features-map` 分支；不要三个人同时推 `main`。
- C 提供功能 DOM/类名及脚本导入需求，B 统一修改 HTML、导航和样式。A 如需修 `js/app.js` 的认证 UI，给 B 明确补丁范围，不同时编辑整份文件。
- 新脚本尚未合入时，B 不提前在页面导入不存在的文件。A 管理依赖和锁文件；C 不自行更换全站框架。
- 每个 PR 写明问题、改动页面、操作步骤、验证结果；涉及界面需提供桌面和手机截图。跨负责人改动先写清交接，再由文件负责人合入。
- 密钥只走本地环境文件或托管平台配置，不发群、不写截图和 Git。生产数据不作为破坏性测试样本。
