# 后端镜像发布清单 · 把 #118 之后的 main 部署到华为云

> 为什么必须单独做这件事：前端（GitHub Pages）随合并自动发布，**API 服务器不会**。
> `docs/team/huawei-backend.md` 已写明「合并 GitHub PR 不会自动更新本机 Docker 镜像」。
> 所以在镜像重建之前，用户打开线上站点仍然会「配不上、答不了题」——修复停在 GitHub 上。

- 线上 API：`https://1.94.225.173`（Caddy 代理 `/api/*`、`/socket.io/*` → 容器 `127.0.0.1:3000`）
- 现役镜像：`xuewuyou-api:f393a37`（对应 main `f393a37` = PR #99），**已落后 main 27 个提交**
- 本次目标：`56f0625e28b4fda1878169e1273eedaf946b15df`（PR #118，匹配队列存活判定）
- 前端：Pages 已 built `56f0625`，**本次不需要动前端**

## 1. 取源码（推荐稀疏克隆，别下整包）

整包 tarball 约 931 MB，而这台服务器只需要几 MB。优先用稀疏克隆：

```bash
cd /opt/xuewuyou/releases
git clone --depth 1 --filter=blob:none --no-checkout https://github.com/Dallovers/xuewuyou.git 56f0625-api
cd 56f0625-api
git sparse-checkout init --no-cone
git sparse-checkout set '/server/' '/services/learning/' '/js/gaoshu_bank.js' '/js/qenhance.js'
git checkout 56f0625e28b4fda1878169e1273eedaf946b15df
```

备选（服务器带宽好的话，最省事）：在能直连 codeload 的机器上取包再传过去。

```bash
curl -L -o xw.tar.gz https://codeload.github.com/Dallovers/xuewuyou/tar.gz/56f0625e28b4fda1878169e1273eedaf946b15df
tar -xzf xw.tar.gz
mv xuewuyou-56f0625e28b4fda1878169e1273eedaf946b15df 56f0625-api
```

## 2. 打包范围（照抄，不要漏 `js/qenhance.js`）

```
Dockerfile.huawei      # 从上一版发布目录或 /opt/xuewuyou/deploy 拷进来
.dockerignore          # 同上
server/                # 整个目录（含 migrations、skin-catalog.json）
services/learning/     # pyBKT 引擎（server/lib/engine.js 用 ../../services/learning）
js/gaoshu_bank.js      # 题库（server/integrations/questions.js 运行时读）
js/qenhance.js         # 新增！见下方说明
```

**为什么 `js/qenhance.js` 是硬需求**：`server/campus/quiz-grader.js` 第 6 行在**模块加载时**就
`readFileSync('../../js/qenhance.js')`，它被 `server/campus/wardrobe.js` 顶层 `require`，
而 `wardrobe` 在 `server/server.js` 启动时注册（第 561 行）。文件缺失 → 抛异常 → **进程起不来**，
现象是容器反复重启、`/api/health` 直接不可用，很容易误判成"新版本有 bug"。

旧清单（f393a37 那次）只有 `Dockerfile、.dockerignore、server、services/learning、js/gaoshu_bank.js`，
`js/qenhance.js` 是这一批（#115 判分/皮肤）之后才需要的，**按旧清单打包必然启动失败**。

依赖无变化：`server/package.json` 与 `f393a37` 完全一致，Dockerfile 里的华为云 npm/pip 镜像源原样沿用，
不需要改构建参数。

## 3. 构建镜像

```bash
cd /opt/xuewuyou/releases/56f0625-api
# 构建文件从上一版发布目录取（一定存在）；deploy 目录里也有一份，哪个在就用哪个
cp ../f393a37-api/Dockerfile.huawei ../f393a37-api/.dockerignore .
# 若上面报 not found，改用：
# cp /opt/xuewuyou/deploy/Dockerfile.huawei /opt/xuewuyou/deploy/.dockerignore .
grep -n '^COPY' Dockerfile.huawei           # 先看它到底把哪些路径搬进镜像
docker build -f Dockerfile.huawei -t xuewuyou-api:56f0625 .
docker images | grep xuewuyou-api          # 新旧两个 tag 都应存在，别删旧的
```

**先看一眼 `COPY` 行**：如果 Dockerfile 是逐条 `COPY js/gaoshu_bank.js /app/js/` 这种写法，
只把文件放进构建上下文还不够，必须补一条 `COPY js/qenhance.js /app/js/`（或把 `js/` 整体拷进去）。
判断标准：构建完后（代码目录沿用旧镜像的 `/app`，先 `docker run --rm --entrypoint sh xuewuyou-api:f393a37 -c 'pwd; ls'` 确认一下）：

```bash
docker run --rm --entrypoint sh xuewuyou-api:56f0625 -c 'ls -l /app/js/qenhance.js /app/js/gaoshu_bank.js'
```

两个文件都在才算打包正确。缺 `qenhance.js` 的表现是容器起来就退出，`docker compose logs app`
里能看到 `Cannot find module` 或 `ENOENT: no such file or directory, open '.../js/qenhance.js'`。

## 4. 切换（保留回退余地）

```bash
cd /opt/xuewuyou/deploy
cp docker-compose.yml docker-compose.yml.bak-f393a37     # 一份可回退的副本
# 把 app 服务的 image 从 xuewuyou-api:f393a37 改成 xuewuyou-api:56f0625
docker compose config | grep image                        # 确认改对了
docker compose up -d app
docker compose ps
```

`/opt/xuewuyou/deploy/.env`（权限 600）**一个字都不要改**：JWT_SECRET、数据库地址沿用，
不要把 `.env`、私钥、备份倒进 Git。

## 5. 验证（约 10 分钟）

```bash
curl --fail https://1.94.225.173/api/health                       # 期望 200 {"ok":true}
curl -s -o /dev/null -w '%{http_code}\n' https://1.94.225.173/api/skins/wallet   # 期望 401（不是 404）
docker compose logs --tail 80 app | grep -iE 'error|throw|Cannot find module'    # 期望无输出
```

`/api/skins/wallet` 返回 404 就是老镜像；401（未登录但路由存在）说明至少带上了皮肤那一批。

**行为验收（这才是本次的重点，单看健康检查不够）**

1. 两个浏览器：一个普通窗口 + 一个无痕窗口（或两台设备），各登录**一个不同账号**。
2. 两个账号都打开 `https://dallovers.github.io/xuewuyou/js/features/campus-hub/index.html?at=arena`，
   走到台前按 `E`。
3. 甲先按 `E`，**在台上等 120 秒以上**（这是原来必挂的场景），乙再按 `E`。

期望：两边几乎同时切到答题面板、各 5 道题、两边显示的作答位不同（甲 / 乙）、对面昵称互相可见。

- 修复前：等满 2 分钟的人会被服务端当幽灵清掉，两人各自"正在匹配对手"，永远配不上。
- 修复后：仍然配上，且甲的座位不被抢走。

再补两个快速回归：交卷后双方都出结果（分数由服务端算）；点「下台」后面板关闭。

## 6. 回退

```bash
cd /opt/xuewuyou/deploy
docker compose stop app
cp docker-compose.yml.bak-f393a37 docker-compose.yml
docker compose up -d app
curl --fail https://1.94.225.173/api/health
```

- **不要回退前端**：Pages 已是 `56f0625`，前端对旧后端是兼容的（本轮只让服务端更宽容，没有新增前端必需事件）。
- 不要 `docker compose down -v`（会删卷）；不要删旧镜像 tag，回退就靠它。

## 7. 三个容易踩的点

1. 服务器在境内，`git clone` 大概率很慢 → 用第 1 节的稀疏克隆；实在不行从本地传包。
2. Caddy 证书约 160 小时由 ACME 自动续期，TCP 80 必须持续可达，别为了"干净"把 80 关掉。
3. 以后每次合并到 main 都要重复第 1~5 步。如果不想每次人工判断，
   可以在 `/api/health` 里带上构建时的 commit（小改动，另开 PR），这样一条 curl 就能看清线上跑的是哪一版。

## 8. 本次发布解决的具体问题（给运维/负责人看的一句话版）

两个真人站在擂台上一起按「开始匹配」时，先等的人会被"排队超时"、"连接被顶号"、"站着 15 秒不动"
这三件事先后判成离线，从匹配队列里消失；后来的人只能跟自己排，于是永远配不上。
本次发布把判定依据从"连接/时间"改成"账号是否还有任意一条连接在线"，并让客户端在断线重连后自动重新入队。
